### **Решение**
[Диаграмма контекста](Context.puml)
[Диаграмма контейнеров](Container.puml)
Было принято решение в переходе на микросервисную архитектуру в долгосрочной перспективе, в дальнейшем это упростит масштабирование, поднимет отказоустойчивость (R1, R2, R3, P1, P2).
Был добавлен API Gateway в качестве единой точки входа для всех запросов, он упрощает процесс миграции на микросервисы, способен перенаправлять трафик при возможных сбоях.
Выделен микросервис по работе с депозитами (+R3).
Хранение актуальных ставок по депозитам и справочной информации по депозитам выделено в отдельную базу данных на Oracle-In-Memory (+R5)
Добавлена очередь сообщений Kafka и дополнительный модуль для преобразования запросов из Kafka в монолит и обратно (+R4).
Для шифрования данных при передаче между фронтом и API Gateway был выбран протокол HTTPS (+R1, +R2).

### **Альтернативы**
1. Не выносить функционал работы с депозитами и с телеком оператором в отдельные микросервисы, модернизировать текущее решение
2. Отказаться от использования Kafka для взаимодействия между сервисами
3. Не переносить данные по актуальным ставкам в БД
4. Не использовать для хранения справочной информации Oracle-In-Memory
5. Использовать другой стек технологий, для чего потребуется дополнительное обучение, либо найм новых сотрудников

**Недостатки, ограничения, риски**

1. Выделение микросервисов по работе с депозитами, СМС и создание очереди сообщений потребует дополнительных ресурсов.
2. У команды нет опыта работы с Kafka, необходимо обучение
3. Для администрирования Kafka и Gateway понадобится DevOps поддержка
